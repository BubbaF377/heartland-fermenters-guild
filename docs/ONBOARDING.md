# Start Here: heartland-fermenters-guild

## What this is
The public site for a real-world hobbyist fermentation/brewing/baking community. It's a static Astro site (GitHub Pages) with a growing recipes section and admin area backed by a managed cloud database, plus a member-contribution feature that's newer than some of the project's own descriptive docs suggest. This guide is about the code and the reasoning behind it, not how to use the site.

## The single most important thing to know before reading any code
**The backend is Firebase (Firestore + Firebase Auth + Cloud Storage) now — not Supabase.** An earlier phase of this project built everything on Supabase (Postgres + RLS), but that was deliberately replaced because Supabase's free tier paused the project after a week of inactivity — a real risk for a low-traffic hobby site with no budget to guarantee uptime. The whole client, schema, and security-rule layer was rebuilt on Firebase rather than patched around the pausing problem.

Practical consequence: if you find a `supabase/schema.sql`, a `src/lib/supabase.js`, or narrative docs describing "Data layer: Supabase" / Postgres RLS as the current architecture, treat that as **history**, not the live design. The exact current Firebase-side file names (client module, `firestore.rules`, storage rules, config) aren't nailed down anywhere in the material this guide is based on — confirm them by looking at the actual repo rather than assuming they mirror the old Supabase layout.

## Read these first, in this order
1. **`docs/PRODUCT.md`** — the hand-maintained source of truth for intent and requirements. Read it before changing behavior. `docs/TEST_PLAN.md`, `docs/USER_MANUAL.md`, and `docs/VISUALIZER.md` are auto-generated *from* it by an external tool ("Devlore"); don't hand-edit those, edit `PRODUCT.md` and let generation catch up.
2. **`src/lib/constants.js`** — categories, slugify helpers, the admin email, time-stage suggestions. Deliberately has no database import, so it's dependency-free and easy to unit test. Good low-risk entry point.
3. **Whatever module is now the Firebase client** (successor to the old `src/lib/supabase.js`) — locate it directly, it isn't named in the history available here.
4. **The current security rules files** (successor to `supabase/schema.sql`, i.e. Firestore/Storage rules) — this is where access control actually lives. The app talks to the database directly from the browser; there is no server of this project's own, so **security enforcement is entirely rules-based, not secret-key-based.**
5. **`src/pages/`** — Astro pages for landing, recipes list/detail, and admin. The recipe detail page intentionally uses a `?slug=` query string instead of a per-recipe static route (see below). There is also now a member-facing sign-in/submission flow (email magic-link) that isn't described in any file-tree listing available here — find it by reading the code, not by assuming a path.

## Why the significant past decisions were made
- **No server, ever.** GitHub Pages serves static output only. Every data operation happens via the vendor SDK directly in browser JS, with correctness enforced by database-side rules (previously Postgres RLS, now Firestore/Storage Security Rules — same principle, different engine). Don't introduce a "backend route" for this app; the architecture assumes there isn't one.
- **`?slug=` instead of `/recipes/<slug>`.** Deliberate: GitHub Pages can only serve pages that existed at the last build, so a freshly-added recipe couldn't have a pre-built static route. Follow this query-string convention for any future per-item page as long as the site stays on GitHub Pages.
- **Supabase → Firebase migration.** Done specifically to remove the free-tier pause risk, accepting Firebase's pay-as-you-go plan and a bit of billing-alert setup instead. This is why Supabase-flavored file names or descriptions may still linger in docs/history without reflecting the live system.
- **Recipe fields (ingredients, instructions, time-stages) are plain newline-separated text, not arrays/structured columns.** Deliberate simplicity trade-off for the admin form and schema. Time-stages are a fully open, freeform per-recipe list; per-category suggested stages are hints only and are never enforced by the schema. Don't "fix" this into rigid structured data without revisiting that call.
- **One shared admin credential, not per-admin accounts**, gates recipe writes. This is intentionally separate from the member system below.
- **Members are a distinct, lower-trust identity model.** Members sign in via passwordless email magic-link against an admin-managed roster — not the admin's shared password, and not full self-serve account signup. Any recipe a member submits lands in a pending queue and requires explicit admin approval before it's public; it is never auto-published. Any future member-generated content should follow the same pattern: separate identity, gated publication.
- **Member roster document IDs are email-or-generated.** A member with an email keeps that as their ID (needed for sign-in lookups); a member without one (common on paper sign-up sheets) gets a generated `no-email-<uuid>` ID instead. Real emails always contain "@" and generated IDs never do, so the two ID spaces can't collide. Always compute a member's ID through the `isEmailId` / `memberIdFor` helpers — don't assume "the ID is the email."
- **Explicit role modeling, not "logged in == authorized."** Early access rules effectively treated "authenticated" as synonymous with "admin," because admin was the only account that could ever log in. Adding member accounts broke that silently — any signed-in member would otherwise have inherited admin-level write access. The fix was to check for explicit roles (an admin check and a separate roster-membership check) and to enforce constraints like "a member's submission must be created as pending" at the database level, not just in the UI. The original implementation of that fix was Postgres-RLS-specific and no longer exists post-Firebase-migration, but **the lesson carries forward**: any new role or account type added to this project has to be checked for explicitly in whatever rules engine is current — never inferred from login status alone.
- **Firestore/Storage rules validate, they don't filter.** This is a real behavioral difference from the old Postgres RLS model: a query that RLS would have silently narrowed to allowed rows can instead be outright rejected by Firestore rules if it isn't shaped the way the rules expect. Keep this in mind when writing or changing any read/write query.
- **Deploy trigger has flip-flopped.** The project has moved between "deploy on every push to `main`" and "deploy only on `v*.*.*` tag push or manual dispatch" more than once — at one point reverting to main-push specifically because build-time config needed to be wired in on every merge, then moving back to tags to stay consistent with an existing tagging convention used elsewhere in the project's tooling. The most recent decision on record favors tag-gated deploys. **Treat that as likely-current but unconfirmed** — the project's own README and `docs/PRODUCT.md` disagree about this at present, and neither the workflow file's actual contents nor a final resolution of that disagreement were available to check. Look at `.github/workflows/deploy.yml` directly before relying on either doc.
- **Devlore's reusable workflows were made public** (rather than restructuring the doc-sync jobs) because GitHub disallows a public repo calling reusable workflows in a private one. If Devlore's repo is ever made private again, the doc-sync automation will break again, by design — that's a known trade-off, not a bug to chase.

## Gotchas: things that look wrong but are deliberate
- `?slug=` query-string routing instead of real per-recipe URLs.
- Ingredients/instructions/time-stages stored as plain text blobs, not structured data.
- Time-stage suggestions per category are hints only; nothing enforces or validates them.
- Member phone numbers are validated only in the admin UI, not in the security rules — deliberately, so an older, still-live version of the site (which writes unvalidated phone data to the same collection) doesn't get broken by a stricter rule deployed underneath it. This is a known, intentionally temporary weak spot: any script or tool that writes to that collection can currently store malformed phone data. It's meant to be revisited once the older site is fully retired — don't "fix" it in isolation without checking whether that older site is still live.
- A single shared admin password gates writes instead of per-admin accounts — intentional, and not the same mechanism as member sign-in.

## Actual mistakes this codebase has made before (not just deliberate-looking oddities)
- The implicit-authorization bug described above: "authenticated" silently meant "admin" until member accounts exposed that as a genuine privilege-escalation hole. It was caught and fixed with explicit role checks — but it's a real example of the kind of mistake to watch for when adding any new account type: check its actual permitted actions explicitly, don't infer them from being logged in.
- **Known, currently-open gap:** editing a recipe's photo does not clean up the previously-uploaded photo file — it's orphaned in storage. Deleting a recipe does clean up correctly; editing doesn't. As of the last recorded state, this hasn't been fixed.

## Testing
Two layers: Vitest for unit tests (e.g. `src/lib/constants.test.js`) and Playwright for e2e (`tests/e2e/*`). The e2e approach changed with the Firebase migration — it now depends on the **Firebase Local Emulator Suite** (and a local Java install) rather than the earlier hand-written Supabase network-mocking helper. If you encounter references to a Supabase mock helper anywhere, that describes the pre-migration test setup, not what to reach for now.

## From clean checkout to a shipped change
1. Clone and install dependencies (standard Astro/npm project — check `package.json`/README for exact commands; not itemized anywhere in the material this guide is based on).
2. You'll need local Firebase configuration (env vars and/or emulator setup) to exercise anything touching recipes, admin, or members — there's no server-side fallback; the app talks to Firebase straight from the browser.
3. Make your change. If it touches who-can-do-what, the actual enforcement point is the Firestore/Storage rules file(s), not the client code — update both together, and sanity-check what a client could do if it ignored your UI entirely.
4. Run Vitest and the Playwright/Firebase-emulator e2e suite before pushing.
5. To ship: merging to `main` may or may not publish the live site depending on which deploy trigger is actually configured right now (see the deploy-trigger note above) — verify against the workflow file, then tag a `vX.Y.Z` release or use manual dispatch if that's what's currently wired up.
6. If your change reflects a change in intent or requirements, update `docs/PRODUCT.md` directly; don't hand-edit the generated docs under `docs/`.
