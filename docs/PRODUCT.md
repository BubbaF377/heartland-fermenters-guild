# heartland-fermenters-guild

The public website for the Heartland Fermenters Guild, a real-world community of home brewers, bakers, picklers, and cheesemakers. Starts as a single landing page and is meant to grow into a full information site with an auth-protected members-only section.

## Vision

Give the guild a real home on the web at `heartlandfermentersguild.org`: first a simple, welcoming landing page people can be pointed to from social media and in person, then over time a fuller site (event info, resources/recipes, an About/history page), and eventually a members-only area gated behind login for guild-specific content.

## Requirements

Hard requirements as they get locked in, separate from the discovery narrative above. Append to this list as decisions firm up.

1. Built with [Astro](https://astro.build), chosen specifically because it ships plain static HTML/CSS for a fast, simple landing page today, while allowing server-rendered pages/endpoints to be added incrementally later (for the members-only section) without a framework migration.
2. Deployed to GitHub Pages via GitHub Actions (`withastro/action`) — build and deploy trigger only when a `v*.*.*` release tag is pushed (same tag pattern the Devlore release workflow listens for), or manually via `workflow_dispatch`. Pushes to `main` alone no longer deploy; cutting a release is now `git tag vX.Y.Z && git push origin vX.Y.Z`.
3. Served at the custom domain `heartlandfermentersguild.org`, registered and DNS-managed on Porkbun (A records pointed at GitHub Pages' IPs, plus a `www` CNAME). Nameservers stay on Porkbun (`*.ns.porkbun.com`) rather than migrating to a provider like Cloudflare, to avoid handing over nameserver control for a single feature. Note: Porkbun's DNS *resolution* backend runs on Cloudflare's network by default for all domains (shown as "DNS Powered by Cloudflare" in Porkbun's dashboard, both view modes) — this isn't an opt-in toggle and can't be disabled. It's DNS-answering infrastructure only, not a traffic proxy: A records resolve directly to GitHub Pages' real IPs rather than Cloudflare's proxy ranges, so it doesn't violate the intent of this requirement (Porkbun/GitHub retain nameserver and traffic control).
4. Repo is public on GitHub (`heartland-fermenters-guild`), linked to Devlore via the create-new-project wizard path. Made public because GitHub Pages for a private repo requires a paid plan (Pro/Team/Enterprise); the site has no secrets in it, so this tradeoff was accepted. To compensate, the repo is locked down: BubbaF377 is the sole collaborator, `main` has branch protection (no force-pushes, no deletion, conversations must resolve before merge), and a repository ruleset blocks anyone without the admin role from creating/updating/deleting `v*` release tags.

Landing page (v1) contains: a header banner image, a short welcome paragraph explaining what the guild is and who it's for, and a "Join the Conversation" section linking out to email, the guild's Facebook Page, its Facebook Group, Instagram, and Meetup. (The guild's circular crest logo, originally shown between the banner and the page title, was removed.) The site-wide footer (in the shared `Layout.astro`, since the recipes/admin pages also use it) shows the copyright notice and Admin link on the left, and "Website development donated by" as plain text next to a Starter Culture Studio logo on the right — only the logo itself links out to `starterculturestudio.com`, not the credit text. The footer stays pinned to the bottom of the viewport even on short pages (e.g. an empty recipe list), rather than floating up under sparse content.
6. Roadmap: expand into a full info site (About/history, Events pages), then add an auth-protected members-only section. Requirement #1's tech stack choice exists specifically to make this addition incremental rather than a rewrite. Recipes (originally listed here as a possible info-site page) shipped as its own database-backed section instead — see Requirements #7–19 (recipes plus the admin and member tooling around them). 7. A recipes section, backed by [Firebase](https://firebase.google.com) — specifically Cloud Firestore, a NoSQL document database. **(Switched from Supabase/Postgres — see History below.)** GitHub Pages can't run server code or reach a database directly, so `/recipes/` and `/recipes/view?slug=...` call Firestore's client SDK straight from the browser using the project's public Firebase web config (`apiKey`, `authDomain`, `projectId`, etc.) — this config is safe to expose client-side, the same trust model the old Supabase publishable key had, and protection comes from Firestore Security Rules, not from keeping it secret. Recipes appear live with no rebuild, which is why the detail page is a single template driven by a `?slug=` query string rather than a pre-built static path per recipe — GitHub Pages can only serve pages that existed at the last build, so a real per-recipe route would mean every new recipe needs a redeploy before it's visible.

    Each recipe is a document in a top-level `recipes` collection, and **the document ID is the recipe's slug itself** (rather than an auto-generated ID with a separate `slug` field) — so slug uniqueness is enforced by Firestore directly (a `create`-only write to an already-existing document ID fails) instead of needing an app-side check-then-write race the way a bare text column would. A new recipe is created in a transaction that tries the title's slug, then `-2`, `-3`, and so on, and never overwrites an existing recipe. A read that's denied (a member can't see pending or deactivated recipes) counts as a taken slug, so a submission can't collide with a recipe its author can't see.

    If recipes can't be loaded (for example, the network is down), the page says so rather than showing an empty "No recipes yet" list.

    **History.** 2026-09-21: migrated from Supabase/Postgres, which the project started on — Requirements #7–16 were all first built against it, including the test suite and the member magic-link system. Supabase's free tier auto-pauses a project after a week of inactivity, a real risk for a low-traffic hobby site; Firebase has no equivalent pause, and Christian was already comfortable in the Google Cloud/Firebase console. The Supabase client, schema, RLS policies, auth flows, and mocked test suite were rebuilt against Firebase rather than re-pointed at a new URL; the recipe field list, pages, and wireframe didn't change. The Supabase build variables came out of the deploy workflow — Firebase's web config is public and committed in `src/lib/firebase.js`. Lists now read from the server rather than a local cache, so a network failure shows an error instead of an empty list.

    2026-09-21: Cloud Storage turned out to need the pay-as-you-go Blaze plan (since February 2026, the free Spark plan has no Storage access). Chose Blaze with a budget alert over dropping photo uploads; the expected cost at guild scale is $0. Rules and indexes are deployed by hand (`firebase deploy --only firestore,storage`), not by the Pages workflow.

8. An admin page (`/admin/`) gates recipe creation behind a login — but a single shared password for the whole guild, not individual accounts ("anyone who has the password can log in"), so there's one fixed Firebase Authentication user (`admin@heartlandfermentersguild.org`, email/password provider) whose password is shared with whoever should have admin access. The password check happens via Firebase Authentication's `signInWithEmailAndPassword` (never a client-side-only comparison, which would be trivially readable in page source) — a successful login just proves "knows the current password," not who someone is. Only that account counts as logged in on `/admin/`: a member signed in on the same browser still sees the password form.

    **History.** 2026-09-21: `/admin/` used to treat any signed-in session as the admin. Once members could sign in (Requirement #16), a member on the same browser saw the admin panel, though every action there failed on the rules. Now only the admin account opens it.
9. Recipe fields: title, category (fixed list — Beer, Wine, Bread & Sourdough, Vegetables & Pickles, Kombucha, Cheese, Other), short summary, an optional photo, an optional how-to video, a freeform yield/servings line, an open list of time stages (Requirement #10), ingredients, instructions, an optional notes/tips field, and an optional submitted-by name. Ingredients and instructions stay plain newline-separated text rather than a structured/array field, to keep the schema and the admin form simple — this same "plain text, one item per line" convention now also covers time stages (Requirement #10). Photo and video (Requirement #11) are independent of each other — a recipe can have a photo, a video, both, or neither.

   This field list — and the recipe detail page layout it feeds — was worked out against a reviewed wireframe based on patterns from popular recipe sites (SideChef, food.com), adapted for a small hobbyist guild: no ratings, no ad-driven layout, no nutrition calculator. See the [recipe page wireframe](https://claude.ai/code/artifact/a0e5e645-1c4e-4d55-a903-18d51f1b2bc0) for the reviewed layout (desktop, mobile, and a second category example), including where each new field sits on the page.

10. Time stages (prep, ferment, rise, bake, age, etc.) are stored as a single optional text field per recipe (`time_stages`), one `Label: Duration` pair per line — the same newline-separated convention as ingredients and instructions, parsed into individual metadata chips at render time (e.g. "Prep: 20 min" becomes a chip labeled "Active Prep" reading "20 min"). This is deliberately an open, repeatable list rather than a fixed set of named columns (no `prep_time` / `ferment_time` / `rise_time` fields): different categories need different sets of stages, and even recipes within the same category can differ — most sourdough recipes are Prep/Rise/Bake, but one that's cold-proofed overnight needs a fourth "Cold Proof" stage, and a fixed field set can't absorb that without a schema change every time a new combination shows up.

    The admin form (Requirement #12) pre-populates suggested starting stages based on the selected category, but the submitter can add, remove, or relabel any stage before saving. Suggested starting points per category:
    - Beer: Prep, Ferment, Condition/Carbonate
    - Wine: Prep, Ferment, Age
    - Bread & Sourdough: Prep, Rise, Bake
    - Vegetables & Pickles: Prep, Ferment
    - Kombucha: Prep, Ferment
    - Cheese: Prep, Culture, Age
    - Other: no suggested stages — added freely

    These are starting suggestions only, never enforced — the stored value is whatever list of stages the submitter actually ends up with, in whatever order they leave them in.

11. An optional recipe photo, uploaded to Firebase Storage under a `recipe-photos/` path; the recipe document stores the uploaded object's storage path (`photo_path`), not a bare public URL, so the display URL is derived at render time via Firebase Storage's `getDownloadURL()`. Upload is limited to the admin (Requirement #8) and active members submitting a recipe (Requirement #16): the Storage Security Rules only accept writes under `recipe-photos/` from those two, and only JPG, PNG, or WebP files up to 10 MB — formats every browser can display — while read access is public (anyone can view a recipe's photo without logging in).

    An optional how-to video, stored as a plain YouTube URL (`video_url`) exactly as pasted by whoever submits the recipe (a `youtube.com/watch?v=...` or `youtu.be/...` link) — the recipe page extracts the video ID at render time to build the embed, rather than asking the submitter to know how to do that themselves. No Firebase Storage involved for video; it's just a link to something already hosted on YouTube.

    **History.** 2026-09-21: the images-only, under-10 MB upload limit was added with the Firebase migration; before it, any authenticated upload was accepted.

    2026-09-21: narrowed from any image type to JPG, PNG, and WebP. HEIC (iPhones' native format) and similar formats can't be displayed by most browsers. iPhones are expected to convert to JPEG automatically when the file picker only offers these types, so iPhone users shouldn't be blocked — **unverified**: widely reported iOS behavior, not yet tried on a device. An iPhone upload through `/admin/` or `/submit/` would settle it; if iOS doesn't convert, iPhone photos in the default HEIC format get refused with the format message.

15. Automated tests: [Vitest](https://vitest.dev) for unit tests, [Playwright](https://playwright.dev) for UI/e2e, both run in CI (`.github/workflows/test.yml`, on every PR and push to `main` — separate from `deploy.yml`, which stays tag-only per Requirement #2). Vitest covers only the pure helpers in `src/lib/constants.js` (slug/list/time-stage/YouTube-URL parsing) — the only framework-free, testable-in-isolation code in the repo; everything else is server-rendered Astro markup or DOM script tied to specific page structure. Playwright runs against the built-and-previewed site (`astro build` + `astro preview`), not `astro dev` — dev and the real production build behave differently for `<script>` tag handling, so testing against dev would validate the wrong artifact.

    Firebase is exercised via the [Firebase Local Emulator Suite](https://firebase.google.com/docs/emulator-suite) (Firestore, Auth, and Storage emulators, started with `firebase emulators:exec` around the Playwright run) rather than a live/staging Firebase project — no secrets needed in CI, deterministic, and it runs the real Firestore/Auth/Storage engines locally instead of hand-mocked REST shapes, which is a step up from the network-interception approach (`page.route()` against Supabase's REST/Auth/Storage URLs) this repo used before the Firebase migration. Security Rules have their own emulator-backed test pass (`npm run test:rules`, using `@firebase/rules-unit-testing`) covering the `isAdmin()`/`isActiveMember()` logic from Requirement #16 — the closest equivalent to verifying the old Postgres RLS policies directly. Real-backend integration tests against a live/staging Firebase project are explicitly out of scope for now. Playwright serves the site on its own port and never reuses a server that's already running.

    **History.** 2026-09-21: Playwright used to reuse whatever server was already on port 4321. A `npm run dev` left running there — which talks to the production Firebase project — once pointed the whole suite at production. No test data got in (the tests' admin logins failed on the test password), but it's why the suite now uses port 4329 and refuses to reuse a server.

16. **Members** (`/submit/`): a second, public-facing login distinct from admin, for guild members to submit a recipe. Explicitly experimental — may not launch, since an open submission form (even members-gated) carries a real risk of an inappropriate photo/image landing in someone's inbox. The pending-by-default design (below) is the deliberate moderation gate for that risk: nothing a member submits ever reaches a public page without an admin approving it first.
    - **Login**: Firebase Authentication's passwordless **email link** sign-in (`sendSignInLinkToEmail` / `signInWithEmailLink`), not a password — chosen specifically because it means "creating a member" is just admin writing an email into a roster collection (`active_members`), with no Firebase Admin SDK or Cloud Function needed anywhere. Authentication is open to any email (that's how email-link login works); *authorization* — whether this email can actually submit — is enforced by Firestore Security Rules against `active_members`, not by the login step. The rules also require the sign-in to have proven the address (`email_verified`), which email-link sign-in does: the email/password provider enabled for admin would otherwise let anyone register an unverified account under a member's email.
    - **Recipe lifecycle**: each recipe document gained a `status` field (`pending` / `published` / `deactivated`, default `published` so every existing and admin-created document needed no migration). A member's create is only ever accepted with `status == 'pending'`, enforced in the Security Rules themselves against the incoming document (the Firestore equivalent of Postgres's `with check`), not just hidden in the UI. The recipe detail page's read is scoped to `status == 'published'` (or an admin session) — a pending or deactivated recipe's detail page therefore fails to load for the public with no extra code, the same 404-like behavior as before.

      One genuine difference from Postgres RLS worth flagging for whoever implements this: Postgres transparently filters which *rows* a query returns, so the old `SELECT *` on the recipes list only ever got back published rows automatically, no matter how the query was written. Firestore Security Rules don't filter documents out of a query result — they only allow or deny the query as a whole. So the recipes-list Security Rule has to explicitly require that any `list` query from a non-admin already includes a `status == 'published'` filter, and the `/recipes/` page code has to actually send that filter — enforcement moves from "automatic no matter what the client asks for" to "the client's query is validated, not silently narrowed." Getting this rule wrong (or forgetting the filter client-side and having a permissive rule) is exactly the kind of thing the Security Rules test pass in Requirement #15 should cover.
    - **Admin gains**: a Members section (list, add a member by name plus an email, a phone number, or both, edit any of those later, deactivate/reactivate — Requirement #14's list already covered recipes; the list shows each member's name with their email and phone beneath it). A member without an email (someone who signed up on paper with just a phone number, say) is stored under a generated ID instead of an email, is marked "No email" in the list, and can't log in or submit recipes until an email is added. Adding, changing, or removing a member's email moves their roster entry to its new ID, keeping whether they're active and when they were added; from then on they log in with the new email (if any), and the old one no longer lets them submit. An email already on the roster can't be taken by another member. A member's phone, when given, must be a 10-digit number; it can be typed in any common format — `4025550134`, `(402) 555-0134`, `402-555-0134`, with dots or spaces, or with a leading `1`/`+1` — is stored as the bare digits, and is always shown as `(402) 555-0134`. Anything else is refused with an explanation and a Pending Recipes queue (Approve → `published`; Reject → hard delete, reusing the same best-effort photo cleanup as an ordinary delete) alongside the existing Recipes list, which itself gained a Deactivate/Reactivate toggle distinct from the existing hard Delete.
    - **Security Rules had to be hardened, not just extended**: every pre-existing "must be authenticated" rule on the `recipes` collection and the `recipe-photos` Storage path implicitly meant "the admin," since admin was the only account that could ever be authenticated. Once members can also hold a real authenticated session, those rules would have let any logged-in member update/delete any recipe or any photo. They're replaced with checks against two reusable Security Rules functions — `isAdmin()` (checks `request.auth.token.email` against the fixed `ADMIN_EMAIL`) and `isActiveMember(email)` (checks the `active_members` collection via `exists()`, without granting the caller broad read access to that collection — the Firestore analog of a Postgres `security definer` function) — so admin-only actions stay admin-only now that "authenticated" no longer implies "admin."
    - Shared recipe-form logic (the time-stage editor, field reading, photo upload) was extracted to `src/lib/recipe-form.js` so the admin add/edit form and the member submission form don't duplicate it.

    **History.** 2026-09-21: a member's slug-collision check used to see only *published* recipes, so a title matching a pending or deactivated recipe failed with a generic error instead of getting a `-2` suffix. The Firebase migration fixed it: recipes are created in a transaction that treats a denied read as a taken slug (Requirement #7).

    2026-09-21: added the verified-email requirement with the Firebase migration.

    2026-09-21: members used to be added by email alone. Admin now also records a name (required) and a phone number (optional); members added earlier show their email in place of a name. Email is still the only thing sign-in checks.

    2026-09-21: members couldn't be changed once added; fixing a name or phone number meant editing the database by hand. Admin can now edit a member's name, email, and phone.

    2026-09-21: phones used to be stored exactly as typed, in any format and with no check on the number of digits. They're now checked for 10 digits, stored as digits, and shown in one format. Phones saved earlier are shown formatted when they hold 10 digits, and as typed otherwise; a member whose earlier phone isn't 10 digits can't be edited until the phone is corrected or cleared. The format is checked on the admin page only, not in firestore.rules: the live v1.2.0 site still saves phones as typed, so a stricter rule deployed before the next release would have broken adding members there.

    2026-09-21: every member used to need an email, since the roster is keyed by email for sign-in. Members can now be added with only a phone number: they're stored under a generated `no-email-…` ID, which can never match a signed-in email (real emails contain `@`; generated IDs never do), so sign-in and firestore.rules needed no change.

20. A `/resources/` page: a searchable, filterable directory of curated fermentation-education resources (authors, organizations, research institutions, reference material) — built from data and a JSON Schema Christian supplied (`fermentation-resource.schema.json` / `fermentation-resources.schema.json`), replacing what could have been a plain table of links.

    Unlike recipes, resource data does **not** live in Firestore: it's a small (61 entries as of this writing), fully pre-researched, single-curator dataset with no submission flow, so it ships as a static JSON file bundled at build time (`src/data/fermentation-resources.json`, matching the supplied schema) and the page filters it entirely client-side — no database read, no Security Rules, no admin login needed to add a resource. Updating the list is a normal content change: edit the file, commit, cut a release (Requirement #2). The supplied schemas live beside it in `src/data/schemas/` (`fermentation-resource.schema.json` for one resource, `fermentation-resources.schema.json` for the list, which references the first by that filename). Whether CI validates the data file against them (so a hand-edit that drops a required field or uses an off-list tag fails the build) is not yet decided — see Open questions.

    Each resource has `name`, `description`, `website` (an external link), `area` (one or more tags from the schema's 47-value controlled enum), `resourceType` (one or more of exactly four: Learn to Ferment, Go Deeper, Safety & Troubleshooting, Organizations & Communities), and `mediaType` (one or more of exactly five: Website, YouTube Channel, YouTube Playlist, Video Collection, Podcast — added in the 2026-09-25 schema update; see History). Of the 47 possible `area` tags, 46 already appear somewhere in the 61-resource dataset — only "Natto" doesn't — so the Area filter is a genuinely long list, not a handful of options; the Type and Media Type filters, by contrast, only ever have 4 and 5 possible values respectively (all of them appear in the data), so both can just be a row of toggle pills with no scrolling.

    The page has:
    - A live search box — filters as you type, no submit button, case-insensitive substring match against `name` and `description` (whether it should also match `area`/`resourceType`/`mediaType` tags is open — see Open questions). No fuzzy-matching library needed at this dataset size (61 rows, entirely in memory).
    - An **Area** filter: grouped into 8 expandable panels rather than one flat list, so the ~46 real tags don't dump onto the page at once. Each panel is independently expandable/collapsible (not an exclusive accordion — more than one can be open at a time) Panel headings are labels that open and close their panel, not filters themselves; the first item inside each open panel is a **Select all** checkbox that selects every tag in it in one click (tri-state: unchecked, checked when all its tags are selected, indeterminate when only some are) — so "all of Beverages" still works as a coarse filter, alongside the specific Wine/Beer/Kombucha/etc. checkboxes. A **"Ask in plain English"** prompt box on `/resources/`, deliberately separate from Requirement #20's live keyword search — a text input plus an explicit **Ask** button (not live-as-you-type), so someone can type a full question ("what can I make with a lot of extra cabbage?") instead of guessing which words the resource descriptions happen to use. On submit, the whole 61-entry dataset (name, description, area, resourceType, and mediaType — never the URLs — with each resource keyed by its position in the bundled data file, so the data needs no ID field; positions only have to agree within one request) is sent as context to a small, cheap language model along with the typed question, and the model returns a capped, structured, ranked list of those positions (any that don't name a real resource are dropped, not rendered) — no retrieval/embeddings pipeline is needed at this dataset size, the same reasoning that kept Requirement #20's dataset out of Firestore in the first place. Matches render in rank order using the same result cards Requirement #20 already defines, under a "Best matches for …" banner; the rail's keyword search and filters still apply, narrowing the matches without re-ranking them, and a **Show all resources** control returns to ordinary browsing. A failed or empty AI response shows a friendly message suggesting the keyword search or filters instead, never a raw error.

    This calls a real, billed LLM API — unlike Requirement #20's search, which is free, client-side, and needs no backend at all. The site stays fully static (GitHub Pages, no server of its own), and a paid LLM API key can never be shipped in browser-served JS the way Firebase's public web config safely is — doing so would let anyone run up the bill. [Firebase AI Logic](https://firebase.google.com/docs/ai-logic), with the **Gemini Developer API** backend, is the mechanism: it proxies the call to Gemini from the client SDK while keeping the actual API key server-side, so no hand-written Cloud Function is needed. Cost and abuse are bounded by several things together, not any single one:
    - **Model**: Gemini Flash-Lite (currently 3.5 Flash-Lite — $0.30/MTok input, $2.50/MTok output, per [Google's Gemini API pricing page](https://ai.google.dev/gemini-api/docs/pricing), checked 2026-09-25). The cheaper 2.5 Flash-Lite isn't available to this project, and 3.1 Flash-Lite was tested and not chosen — see History.
    - **No live-as-you-type calls** — a query only fires on an explicit Ask-button submit, unlike Requirement #20's keyword search.
    - **The whole dataset in every request, nothing more** — no conversation history, no retrieval step, no chained calls.
    - **Capped, structured output** — the model is asked for a short JSON list of identifiers (roughly a top 8), not freeform prose, keeping output tokens small and predictable. The instructions also tell it to prefer resources whose media type matches when the question asks for one ("videos about koji").
    - **[Firebase App Check](https://firebase.google.com/docs/app-check)** — enforced on AI Logic calls only, so only the guild's own deployed site can call the model — not a scraped copy of the config or a bot. Firestore and Storage stay unenforced, so the recipes, admin, and submit pages and the emulator-based tests need no App Check setup.
    - **Firebase AI Logic's built-in per-user rate limit** — **5 questions per minute per visitor**, in every region (the Google Cloud quota "Generate content requests per minute per project per user"; default 100). It's per minute only — AI Logic has no daily per-visitor cap — so it slows a single visitor down rather than capping them. **Not observed working:** in testing the same day, 22 requests from one browser in about 90 seconds all succeeded — see Open questions. A visitor who does get a rate-limit refusal (a 429 that isn't about money) is told they've asked several questions quickly and to wait a minute.
- **Prepaid Gemini credits** — the Gemini Developer API bills through Google AI Studio's prepaid credits, and refuses requests once they run out, so the most that can ever be spent is the balance on hand. This is the actual spending ceiling; keep the balance modest. Google's billing docs (checked 2026-09-25) describe no low-balance alerts for prepaid credits; they do describe a per-project **monthly spend cap** in AI Studio (**Spend → Monthly spend cap → Edit spend cap**) and optional auto-reload with its own monthly limit. Auto-reload should stay off so running out stays a hard stop. When the money runs out — the spend cap is reached, or the credits are used up — the Ask box shows a notice that the plain-English search is paused for now and that searching and filtering still work, and it disables the Ask box for the rest of the visit instead of failing on every try. It recognizes that case by any money-related wording in the error (spend, billing, budget, prepay, credit, payment) or an HTTP 402, since only the credits error has actually been seen. Any other failure shows the general "isn't working right now" message.
    - **The existing Blaze budget alert** (Requirement #7's History) covering Gemini API spend (whether it already does, or needs extending, is unchecked — see Open questions), so an unexpected spike is caught rather than discovered on a bill.

    Measured on 2026-09-25 with the 61-entry dataset: about 4,750 input tokens (dataset plus instructions) and about 26 output tokens per search, with no thinking tokens — about **$0.0015 per search** on 3.5 Flash-Lite, so even a very active month (1,000 searches) lands around **$1.50**. Answers take about 1 second. Real usage is expected to be far lower for a hobby-guild site; the rate limit and budget alert exist as a backstop against abuse, not because ordinary use is expected to approach these numbers.
